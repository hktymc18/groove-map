# セミナー受付・稼働率管理システム 設計書（GROOVE CHECK-IN 仮称）

## 1. 現状の整理（ANTARES.numbers の分析結果）

現在の運用は Numbers ファイル + USB型QRコードリーダーの組み合わせ。

- **QRコードSS シート**: 約2,200名の名簿マスタ（QRコード番号・氏名・UPBD系列・性別）
- **日付別シート（0901_SYS 等）**: 受付でQRカードをスキャン → リーダーがキーボード入力として
  番号をA列に打ち込む → VLOOKUP で氏名・系列を解決 → COUNTIF で系列別に集計
- **原本シート**: セミナーごとに複製して使うテンプレート
- カードを忘れた人は「カードなし」行で手動対応

### 課題

1. セミナーごとにシートを複製する手作業
2. 稼働率は別の稼働表 Numbers に**手転記**
3. MAP（groove-map）の稼働率（actRate）にも**手入力**
4. ファイルが1台のMacに閉じており、他ユニオンへの横展開ができない
5. VLOOKUP の参照範囲（$A$2:$C$2400）が名簿の増加で溢れるリスク

つまり同じ出席データを **3回** 入力している。1回の受付操作ですべて自動化するのが本設計の目的。

## 2. 提案の概要

**受付用のWebアプリ（PWA）を作り、スキャン結果を直接 Firestore に書き込む。**
稼働率は自動計算され、MAP が読み取って actRate に反映する。

```
[受付タブレット/PC]                       [Firestore]                [MAP]
 QRリーダー or カメラでスキャン ──書込──▶ unions/{id}/events/…/attendance
 リアルタイム系列別集計を表示 ◀─購読──          │
                                        月次自動集計 stats/{yyyymm}
                                                 │
                              MAP「稼働率取込」──読取──▶ actRate 自動更新
```

- Numbers・稼働表・手入力がすべて不要になる
- 技術構成は MAP と同じ（シングルファイル HTML + Firebase + GitHub Pages）なので
  運用コスト・学習コストが増えない

## 3. 出欠確認方式の設計判断

| 方式 | 現地確認 | 受付の即時確認 | 備考 |
|---|---|---|---|
| A. 受付スキャン（推奨・主軸） | ◎ 受付が本人を見て処理 | ◎ 画面に氏名が出る | 既存QRカード・USBリーダーが**そのまま使える** |
| B. スマホ会員証（追加） | ◎ 受付が本人を見て処理 | ◎ 同上 | アプリが本人のQRを表示。「カードなし」問題が解消 |
| C. 当日コード自己申告（オプション） | △ コードが漏れると遠隔出席が可能 | ○ ライブボード+受付承認で担保 | 行列の解消に有効。下記の二段階方式で弱点を補う |

### 方式Cの設計（当日パスワード案の改良版）

ユーザー案の「当日のパスワードを入力して出席」は、そのままだとコードを欠席者に
共有できてしまう。そこで**二段階（申告→受付承認）**にする:

1. イベント作成時に4桁の当日コードを自動生成。会場掲示または口頭で伝える
2. 本人がスマホでコード入力 → 出席レコードが `status: pending` で作成される
3. 受付タブレットの**ライブボード**に名前がポップアップ表示（効果音つき）
4. 受付が本人の顔を見てタップ → `status: confirmed` に更新、本人のスマホに✓表示

これで「現地に来たことの担保」と「受付がその場で処理したことが分かる」の両方を満たす。
コードはイベントの開催時間帯のみ有効。

**推奨**: フェーズ1はA（既存の運用と同じ体感、移行コストほぼゼロ）。B・Cは後続フェーズ。

## 4. データベース設計

### 4.1 配置方針

**MAPと同じ Firebaseプロジェクト（hotlist-21865）内に、独立したトップレベル
コレクション `unions/` を作る。**

- アプリ・リポジトリ・URLは MAP と別（論理的には別システム）
- ただし同じ Firestore・同じ Firebase Auth を共有 → MAP がログインユーザーのまま
  出席統計を直接読めるので、稼働率連携が**クライアント側だけで完結**する
- 完全に別プロジェクトにすると、連携に Cloud Functions か二重ログインが必要になり
  「稼働率を手で入れなくてよくなる」というメリットが遠のく
- MAP の既存コレクション（users/, maps/, sharedWith/）には一切触れない

### 4.2 コレクション構造

```
unions/{unionId}                          … ユニオン（チーム）。横展開の単位
  name, area, ownerUid,
  admins: [uid, ...],                     … 管理者（受付担当を含む）
  createdAt

unions/{unionId}/members/{memberId}       … memberId = 既存のQRコード番号（例 "412211"）
  name, kana, gender,
  group,                                  … UPBD系列（"馬越BD" 等）
  active: true,
  mapLink: { uid, memberId } | null       … MAP側メンバーとのヒモ付け（任意）

unions/{unionId}/events/{eventId}         … eventId = "20250901_SYS" 等
  date, name,                             … "SYS", "B-T", "P&P" 等
  checkinCode,                            … 当日コード（方式C用、4桁）
  selfCheckinOpen: false,                 … セルフチェックイン受付中フラグ
  createdBy, createdAt

unions/{unionId}/events/{eventId}/attendance/{memberId}
  memberId, name, group,                  … 非正規化（集計を1クエリで済ませるため）
  method: "qr" | "self" | "manual",
  status: "confirmed" | "pending",
  checkedInAt, confirmedBy
  ※ ゲスト（名簿外）は memberId の代わりに "guest_xxx" + 氏名手入力

unions/{unionId}/stats/{yyyymm}           … 月次集計（出席確定時に更新）
  eventsHeld: 12,
  perMember: { "412211": { attended: 10, rate: 83 }, ... },
  perGroup:  { "馬越BD": { totalAttendance: 145 }, ... }
```

ドキュメントIDに既存のQRコード番号をそのまま使うので、**今のQRカードとUSBリーダーが
一切変更なしで動く**（リーダーは番号をキー入力するだけなので、入力欄にフォーカスが
あれば Numbers でも Web でも同じ）。

### 4.3 セキュリティルール（追記分）

```
match /unions/{unionId} {
  function isAdmin() {
    return request.auth != null &&
      request.auth.uid in get(/databases/$(database)/documents/unions/$(unionId)).data.admins;
  }
  allow read: if request.auth != null;          // 稼働率取込のため認証ユーザーは読取可
  allow write: if isAdmin();
  match /{document=**} {
    allow read: if request.auth != null;
    allow write: if isAdmin();
  }
  // 方式C導入時: attendance への pending 作成のみ本人にも許可するルールを追加
}
```

※ 読取範囲を「同ユニオンのメンバーのみ」に絞りたくなったら、users/{uid} に
unionId を持たせて絞り込む（フェーズ4で判断）。

## 5. 稼働率の自動計算と MAP 連携

### 5.1 計算

- 出席が確定するたびに `stats/{yyyymm}` をインクリメント更新（クライアント側、
  Cloud Functions 不要）
- `rate = attended ÷ eventsHeld × 100`（当月の開催数分母）
- 集計画面に「再計算」ボタンを置き、attendance を舐めて stats を作り直せるようにする
  （二重スキャン取消などの修正に対応）

### 5.2 MAP 連携（actRate 自動反映）

MAP 側に「稼働率取込」ボタンを1つ追加する:

1. ログインユーザーが admin になっている union の `stats/{当月}` を読む
2. MAP の現状メンバーと出席名簿を **姓+名の一致** で自動マッチング
3. 一致しなかった分は手動ヒモ付けモーダルで対応 → `mapLink` に保存され次回から自動
4. 確認画面（変更プレビュー）を出してから actRate を一括更新

MAP は compat SDK のままで実装可能（同一プロジェクト・同一認証のため追加設定なし）。

## 6. 画面設計

### 6.1 受付モード（キオスク画面）— フェーズ1の中核

- 画面全体が入力欄（常時フォーカス）。USBリーダーで「ピッ」→ 即座に
  **氏名・系列を大きく表示 + 緑フラッシュ + 効果音**
- タブレット運用時はカメラでのQRスキャンも可（BarcodeDetector API + フォールバック）
- 重複スキャンは黄色で「出席済みです」表示（記録は増えない）
- 未登録番号 → ゲスト登録ミニフォーム（氏名+紹介者系列を選択）
- サイドパネルに**系列別リアルタイム集計**（現在の COUNTIF 表の置き換え。
  Firestore onSnapshot で複数端末でも同期）
- **オフライン対応**: Firestore のオフライン永続化により、会場の電波が悪くても
  スキャンは端末に貯まり、回復後に自動送信

### 6.2 その他の画面

- **イベント管理**: 作成（日付・種別）、当日コード自動生成、開催履歴
- **メンバー管理**: 名簿CRUD、CSVインポート/エクスポート、QRカード一括印刷ページ
  （番号→QR画像生成。新規メンバーのカード発行が内製化できる）
- **集計**: 月次マトリクス（メンバー×イベント。稼働表の置き換え）、系列別集計、
  月次推移、CSV出力
- **セルフチェックイン**（フェーズ3）: コード入力画面 + 受付ライブボード（承認フロー）

## 7. 横展開（マルチテナント）

- すべてのデータが `unions/{unionId}` 配下 → **ユニオン追加 = ドキュメント1つ作るだけ**
- 新ユニオンのオンボーディング: ①ユニオン作成 → ②名簿CSVインポート →
  ③QRカード印刷 → ④受付タブレットでログイン、の4ステップ
- アプリは1つのURL（GitHub Pages）を全ユニオンで共有。ログインユーザーの
  所属ユニオンを自動選択
- 費用: Firebase 無料枠内に余裕で収まる想定
  （書込 = 出席数 ≒ 数千/月、無料枠は 2万/日。ホスティングは GitHub Pages で無料）

## 8. 移行

- 名簿: 今回の ANTARES.numbers の「QRコードSS」シート（2,196名）をそのまま
  CSV化してインポート（機械的に抽出可能なことは確認済み）
- 過去の出席データ: 必要なら日付別シートも同様にインポート可能
- 並行期間: 1〜2回のセミナーで Numbers と併用し、集計が一致することを確認してから切替
